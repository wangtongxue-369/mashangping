## 1. 项目概述

"码上评"是一套面向高校程序设计课程的**在线编程与智能评阅一体化平台**，形成完整教学闭环：

> 在线编程 → 自动评测 → 代码分析 → 查重检测 → 智能反馈 → 教学数据分析

学生直接在系统中阅读题目、编写并提交代码，系统通过测试数据自动判分；平台进一步基于抽象语法树（AST）对代码做结构化分析，实现抗改名查重、多维代码质量评价与针对性改进建议，最终以班级数据看板呈现成绩分布、代码质量、常见错误与相似度信息。

## 2. 定位与已确认约束

| 维度 | 结论 |
|---|---|
| 项目定位 | 真实落地的高校教学产品，稳定性和易用性优先 |
| 编程语言 | C/C++、Java、Python 三种（架构按语言可插拔设计） |
| 用户规模 | 单课程/几个班，<200 学生，单机可承载 |
| 智能反馈 | 纯规则模板确定性生成，不依赖 LLM |
| 技术栈 | Java 后端 + React 前端 |
| 部署环境 | 云服务器，Docker 可用 |
| 查重范围 | 仅同班互比（首发） |

## 3. 总体路线图：分期垂直交付

项目横跨 4 个子系统，拆分为 3 期交付，每期都是完整可用产品：

```
第一期（本文档详设）          第二期                    第三期
P0 教学底座 + P1 在线评测  →  P2 代码分析            →  P3 数据看板
用户/课程/班级/作业/题库      AST解析/质量评分           学生反馈页强化
在线编辑器/提交/沙箱判题      同班查重/规则建议库         教师数据看板
```

依赖关系严格单向：无 P0 无法发题；无 P1 提交数据则分析无从谈起；无 P2 分析结果则看板无米下炊。

第二期、第三期启动时各自独立走 brainstorm → spec → plan 流程细化，本文档只锁定其边界。

## 4. 第一期功能范围

### 教师端
- 课程管理：建课、生成选课邀请码
- 学生管理：Excel 批量导入名单
- 题库管理：题目增删改查（Markdown 题面）、测试用例管理（样例点/隐藏点）
- 作业发布：从题库选题、配置各题分值、起止时间、迟交宽限期
- 提交记录：查看任意学生的全部历史提交（代码原文 + 判题明细 + 用时内存）
- 成绩册：按作业自动汇总（取最高分），CSV 导出

### 学生端
- 选课：输入邀请码加入课程
- 作业列表与题目阅读（作业开始前不可见题目内容）
- Monaco Editor 在线编码，选择语言后提交
- 判题进度实时推送（排队中 → 编译 → 逐测试点结果）
- 结果查看：样例点可见完整输入输出；隐藏点仅显示通过与否
- 个人成绩查询

### 管理端
- ADMIN 用户管理（最小实现：账号启用/停用、重置密码）

## 5. 架构设计

### 5.1 架构形态

单机单体架构，一台云主机承载全部组件：

```
浏览器 (React SPA)
   │ HTTPS
   ▼
┌─────────────────────────────────────────────┐
│  云主机                                       │
│                                             │
│  ┌───────────────────────┐                  │
│  │ Spring Boot 单体应用    │                  │
│  │  · REST API            │                  │
│  │  · 认证授权             │                  │
│  │  · 判题调度器(内嵌)      │──┐               │
│  └───────────────────────┘  │ docker-java    │
│                             ▼                │
│  ┌─────────────────────────────────────────┐│
│  │ Docker Engine                            ││
│  │  ├─ 沙箱容器×N（每次判题一个，用完即毁）       ││
│  │  │   gcc / jdk / python 三种语言镜像       ││
│  └─────────────────────────────────────────┘│
│  MySQL（业务数据 + 判题队列表）                  │
└─────────────────────────────────────────────┘
```

### 5.2 关键决策及理由

1. **判题不做独立服务，作为应用内嵌模块。** 通过 `docker-java` 直接操控本机 Docker，为每次提交启动一次性沙箱容器；判题任务用 MySQL 队列表而非 Redis/RabbitMQ——200 人规模下数据库队列完全够用，且天然获得任务持久化、状态可视与崩溃恢复。部署单元最少（应用 + Docker + MySQL），故障面最小。
2. **沙箱 = 一次性 Docker 容器。** 按语言预置三个判题镜像；容器内低权限用户执行"编译 → 逐测试点运行"，施加资源限制与墙钟超时。这是 QDUOJ 等成熟 OJ 验证过的路线。
3. **前端**：React + Vite + Ant Design + Monaco Editor 在线编码。

### 5.3 技术栈清单

| 层 | 选型 |
|---|---|
| 后端框架 | Java 17 + Spring Boot 3.x |
| 数据库 | MySQL 8 |
| ORM | MyBatis-Plus |
| 判题驱动 | docker-java |
| 前端 | React 18 + Vite + TypeScript + Ant Design 5 |
| 代码编辑器 | Monaco Editor |
| 部署 | 主机上 docker compose 编排（MySQL + 应用），应用自身再调 Docker |

### 5.4 认证方案

JWT + Spring Security；账号密码登录 + Excel 批量导入学生名单；预留学校统一认证扩展接口，首发不实现。

## 6. 数据模型

### 6.1 实体关系

```
User 用户          Course 课程         Assignment 作业        Problem 题目
·username          ·name               ·course_id            ·course_id
·real_name         ·term 学期          ·title/description    ·title/description(MD)
·student_no 学号    ·teacher_id         ·start_at / due_at    ·allowed_languages[]
·role: ADMIN       ·join_code 选课码    ·late_policy 迟交策略   ·time_limit_ms
 /TEACHER/STUDENT                      ·总分校间关联表汇总      ·memory_limit_mb
                                            │                     │
              Enrollment 选课               │                     │
              ·course_id + user_id          ▼                     ▼
              ·unique约束            AssignmentProblem      TestCase 测试点
                                    ·assignment_id         ·problem_id
                                    ·problem_id            ·input / expected_output
                                    ·score 该题分值         ·is_sample 样例/隐藏
                                                           ·score_weight 分值权重

Submission 提交                    JudgeTask 判题任务(DB队列)     JudgeDetail 判题明细
·problem_id + user_id              ·submission_id               ·submission_id
·language / code                   ·status: PENDING/RUNNING     ·test_case_id
·status: AC/WA/TLE/MLE/RE/CE…      /DONE/FAILED                 ·status / 用时 / 内存
·score / passed_count              ·retry_count / heartbeat     ·message(按可见性过滤)
·submitted_at / is_late
```

### 6.2 设计要点

- **题目挂在课程下**而非作业下，同一道题可在多个作业复用；`AssignmentProblem` 决定某次作业包含哪些题、各占多少分。
- **判题队列表 `JudgeTask` 即持久化队列**；应用重启时把遗留 RUNNING 重置回 PENDING，天然获得崩溃恢复。
- **测试点存 MySQL**（教学题目输入输出均为小文本，不引入对象存储）。
- **Submission 全量保留历史**，教师端可查看任意学生的完整提交记录；学生成绩取同题最高分。

## 7. 判题流水线

```
学生提交 ──▶ ① Submission(PENDING) + JudgeTask(PENDING) 落库，立即返回
                │
调度器(线程池, 并发上限默认3, 可配置) ──▶ ② 领任务标 RUNNING
                │
③ 启动一次性沙箱容器（按语言选镜像）
   挂载代码与测试数据(只读) | 内存/CPU/pids限制 | 禁网络 | 墙钟超时兜底
                │
④ 容器内执行：编译(C:gcc / Java:javac / Python:py_compile)
   ├─ 编译失败 → CE，结束
   └─ 逐测试点：喂stdin → 运行(timeout+ulimit) → 抓stdout/退出码 → 与期望输出比对
                │
⑤ 写回结果(状态/得分/逐点明细) ──▶ ⑥ finally 强制销毁容器
```

细节说明：
- **输出比对**：忽略行尾空白、忽略文末多余空行（OJ 惯例），其余精确匹配；比对器抽成接口，为 Special Judge 留扩展点，首发不实现。
- **Java 特殊照顾**：JVM 启动慢且吃内存，Java 题时间限制放大系数 ×2、容器内存下限提高，避免"本地能跑线上全 TLE"。
- **实时反馈**：提交后 WebSocket 推送判题进度（排队中→编译→逐点结果），前端不轮询。
- **崩溃恢复**：调度器启动时将遗留 RUNNING 任务重置为 PENDING 自动续跑。

## 8. 业务规则（已确认）

| # | 规则 | 结论 |
|---|---|---|
| 1 | 多次提交 | 全部保留历史，**取最高分**计入成绩；教师后台可见完整提交记录 |
| 2 | 迟交 | 教师可为每个作业配置宽限期(0~7天)；期内可交但标记迟交，成绩照常参与"取最高分"；超过宽限期关闭提交入口 |
| 3 | 角色体系 | ADMIN / TEACHER / STUDENT 三种；不做助教，字段预留 |
| 4 | 隐藏测试点 | 学生可见样例点的完整输入输出；隐藏点只显示"第X个测试点未通过"，不暴露输入输出内容 |
| 5 | 题目可见时机 | 作业 `start_at` 之前学生不可见题目 |
| 6 | 成绩册 | 按作业自动汇总，CSV 导出 |

## 9. 安全设计

### 9.1 沙箱防护（纵深防御）

| 层 | 措施 |
|---|---|
| 隔离 | 每次提交独立一次性容器，判完即毁；容器内非 root 低权限用户执行 |
| 网络 | `--network none` 彻底断网 |
| 资源 | 内存 limit、CPU 配额、`pids-limit`（防 fork 炸弹）、墙钟超时强杀 |
| 文件 | 只读根文件系统 + 小容量 tmpfs 可写区；测试数据判完随容器销毁 |
| 泄漏 | 隐藏测试点的输入输出永不进入任何学生可达的接口响应 |

后续硬化预留：可切换 gVisor (`runsc`) 运行时获得更强内核隔离，首发不实现。

### 9.2 应用层安全

- Spring Security 角色控制 + **数据归属链校验**（学生只能访问自己选的课程里自己的提交；教师只能管理自己开的课），权限校验统一放 service 层强制执行，重点防横向越权读取他人代码。
- BCrypt 存储密码；JWT 有效期 24h；Markdown 渲染经白名单消毒防 XSS；MyBatis-Plus 参数化查询。
- 提交限流：同一学生对同一题 10 秒内不可重复提交。

## 10. 错误处理

| 场景 | 处理 |
|---|---|
| 判题中途异常（容器启动失败等） | JudgeTask 标 FAILED 自动重试 ≤2 次；仍失败则该提交标"系统错误"，教师端可见告警，学生端友好提示且不计成绩、不锁提交 |
| 应用崩溃重启 | 启动时将遗留 RUNNING 任务重置为 PENDING，自动续跑 |
| Docker daemon 故障 | 提交照常入库排队，前端显示"评测排队中"，恢复后自动消化积压 |
| 前端 | 统一拦截：401 跳登录、403 明确提示、5xx 友好页 |

## 11. 测试策略

1. **判题流水线集成测试（项目测试重心）**：Testcontainers 起真实容器，三种语言各备一套标准题集，覆盖 AC / WA / TLE / MLE / RE / CE 全部状态，含死循环、fork 炸弹、超大输出等恶意样例。
2. 后端单测：JUnit 5 + Mockito，重点覆盖成绩汇总（取最高分）、迟交判定、越权链路。
3. API 冒烟：关键路径 MockMvc 测试。
4. 前端：Vitest 少量关键组件测试 + 手工验收清单。
5. 运维基线：docker compose 一键部署；MySQL 每日定时 dump 备份；日志轮转。

## 12. 为第二、三期预留的接口

| 预留点 | 说明 |
|---|---|
| `Submission.code / language` | 第二期 AST 分析器的直接输入，无需改动一期结构 |
| 输出比对器接口 | 第二期如需 Special Judge 可插拔实现 |
| User 助教字段 | 角色字段设计为可扩展枚举，未来加 TA 不改表 |
| 容器运行时参数化 | 判题容器的 runtime 参数可配置，为 gVisor 切换留位 |
| `JudgeDetail` 结构 | JSON message 字段可容纳第二期的质量分析结果引用 |

## 13. 非目标（明确不做）

- 不做 LLM 生成的任何反馈或评审
- 不做跨学期历史库比对、网络公开代码库比对
- 不做助教角色
- 不做 Special Judge（仅留接口）
- 不做移动端 App
- 不做多机分布式判题
- 不对接学校统一认证（仅留扩展点）
